## 1. 执行摘要

CapsWriter-Offline 已经不是简单的语音识别脚本，而是一套围绕 Windows 低延迟输入建立的完整桌面系统：它具备客户端/服务端分离、独立推理进程、多模型抽象、实时听写、文件转录、时间戳拼接、热词纠错、LLM 角色、托盘 UI 和本地归档。核心业务方向清晰，实用性强，多个模块已经具有良好的职责划分。

2026-08-08 的集中修复已经补上首轮工程护栏：修复了未初始化的音频生命周期锁；WebSocket 默认仅监听回环地址，LAN 模式强制令牌并可配置 TLS；消息、任务、缓存、连接和多进程队列均增加资源上限；缓存按 `task_id` 隔离；Worker 改为可验证的 round-robin；并建立 pytest、coverage、ruff、mypy、pre-commit、Windows CI 与发布 smoke 配置。无模型自动测试当前覆盖协议边界、调度、文本处理、配置兼容和音频生命周期 mock。

当前主要风险已经从“确定性故障和无边界网络入口”转向“剩余生命周期竞态与发布可复现性”：音频重开虽由 `RLock` 串行化，但仍依赖 sounddevice 私有驱动重载 API，finished callback 仍可能创建多个后台重开线程，退出时也没有完整 join；依赖仍未锁定；LLM 密钥、数据留存和云端外发仍缺少统一控制面；新增 CI 与发布 smoke 尚需在 GitHub 和 Windows 实机上持续验证。

综合判断：

- 个人本机、受信网络、熟悉配置的用户：默认回环模式和资源上限已显著降低风险，功能成熟度中上。
- 面向普通用户发布：仍需补齐首次运行诊断、配置校验、依赖锁定、升级兼容和 Windows 实机回归。
- 允许局域网客户端接入：现在必须显式启用 LAN 模式和强令牌；普通 `ws://` 仍只适合可信局域网，跨不可信网络必须启用 TLS 或可信反向代理。
- 继续快速迭代：已有自动化基线，应继续提高关键路径覆盖率并建设可观测性，防止音频、线程和协议问题回归。

建议把近期目标定义为：完成剩余的音频生命周期控制器、依赖/密钥/隐私收口和 Windows 实机验证，再开发配置中心、批量转录和更丰富的 LLM/热词体验。

- 语言与平台：Python，Windows 10/11 优先。

- 网络：WebSocket JSON 消息，音频以 Base64 编码；可选 UDP 广播与控制。
- 推理：ONNX Runtime/DirectML、GGUF/Vulkan、sherpa-onnx，多套 ASR/标点/对齐器。
- 桌面 UI：Tkinter、pystray、Rich、模拟键盘与剪贴板。
- LLM：OpenAI 兼容接口、Ollama、LM Studio 及多个云 Provider，角色文件热加载。
- 分发：PyInstaller。

### 2.3 主数据流

```text
全局快捷键/UDP
      ↓
Client AudioStream → asyncio.Queue → AudioRecorder
      ↓                               ↓ 本地音频/日记
   sounddevice                 WebSocket / Base64
                                      ↓

                                      ↓
```

## 3. 做得好的地方

### 3.1 架构方向正确

服务端把模型推理放入独立进程，避免 CPU/GPU 推理阻塞 WebSocket 心跳和消息收发；客户端把音频采集、快捷键、输出、转录、LLM 和热词分成独立模块。`Task`、`Result`、`AudioMessage`、`RecognitionMessage` 让跨层数据有明确载体，这为后续测试和协议版本化提供了良好基础。

### 3.2 模型能力抽象具有扩展性

引擎工厂和能力标志能根据 ASR 是否自带标点/时间戳决定是否外挂模型，对齐器采用延迟加载和闲置卸载。它减少了不同模型路径对主流程的侵入，也适合后续增加模型健康检查、基准测试和插件注册。

### 3.3 用户工作流完整

项目不仅解决“语音转文字”，还覆盖输入触发、低延迟上屏、热词纠错、文件字幕、托盘、日记、LLM 角色和多应用输出差异。特别是热词的音素检索、token 时间戳合并和文件转录链路，形成了明显的产品特色。

### 3.4 本地优先意识较强

模型、录音、日记和日志主要保存在本地，默认客户端连接回环地址；模型目录和用户数据目录已被 `.gitignore` 排除。项目也明确说明 Windows 与离线使用场景，定位比追求全平台更实际。

## 6. 发现详解与修复建议

### AUD-01：音频锁没有初始化（高）

修复状态：已完成。`AudioStreamManager.__init__()` 现在显式创建 `threading.RLock()`；`start()`、`stop()`、`reopen()` 和设备监控的共享状态检查均进入同一生命周期锁。使用可重入锁是因为 `reopen()` 会嵌套调用 `stop()` 与 `start()`。单元测试已覆盖锁初始化、启动/停止幂等、重开顺序以及 finished callback 不在 PortAudio 回调线程内直接关闭流。

原始证据（修复前）：设备监控和 `reopen()` 使用 `self._stream_lock`，但构造函数没有创建该锁。设备监控会触发 `AttributeError` 并被宽泛异常捕获，异常重开线程则直接失败。

剩余工作归入 AUD-10：

1. 将启动、停止、重开收敛到显式状态机。
2. 增加 single-flight 标志，避免多个 finished callback 排队创建多个重启线程。
3. 退出时设置停止事件并 join 监控/重启线程（带短超时）。
4. 在 Windows 实机覆盖设备拔插、暂停/恢复与退出竞态。

### AUD-02：WebSocket 默认暴露且无认证（高）

修复状态：已完成。服务端默认 `network_mode = 'local'`、`addr = '127.0.0.1'`，且 local 模式拒绝非回环监听地址。LAN 模式必须显式配置并从 `CAPSWRITER_AUTH_TOKEN` 读取至少 32 字符令牌，服务端在握手阶段使用常量时间比较验证 Bearer token；客户端兼容不同 websockets 版本发送认证 Header。服务端可加载证书与私钥启用 TLS，客户端会切换为 `wss://` 并校验证书链和主机名。

配套文档：`docs/局域网连接安全配置.md` 说明了本机模式、LAN 令牌生成、TLS 配置、反向代理边界和明文 `ws://` 的适用范围；README 已增加入口。

原始证据（修复前）：服务端默认 `0.0.0.0`，客户端固定使用 `ws://`，握手没有认证或 TLS。同网段设备只要通过防火墙即可提交任务并占用推理资源。

后续建议：增加令牌轮换/撤销、活跃客户端管理和认证失败限频；跨不可信网络继续要求 `wss://` 或可信反向代理，不应把携带令牌的明文 `ws://` 暴露到公网。

### AUD-03：输入、缓存和队列无资源上限（高）

修复状态：已完成。当前实现对 WebSocket 消息/接收队列、并发连接、单连接任务数、单消息与单任务音频、context、空闲连接、任务时长、多进程队列及 Worker 内部缓冲设置了可配置上限；协议入口严格校验字段类型、有限数值、来源枚举、Base64 和 float32 字节对齐。音频缓存已改为按 `task_id` 隔离的 `bytearray`，队列满时以 WebSocket 1013 明确通知“服务器繁忙”，文件转录通过有限在途窗口并发收发以承接背压。

原始证据（修复前）：服务端和客户端 WebSocket 均设置 `max_size=None`，客户端还设置 `max_queue=None`。服务端 `AudioCache.chunks += data` 可无限增长，`multiprocessing.Queue` 默认无界。`AudioMessage.from_dict()` 没有运行时校验 `source`、字段类型、Base64、`seg_duration`、`seg_overlap`、context 长度或音频字节对齐。

影响：过大消息、永不发送 final、极端切片参数或消息洪泛可造成内存持续增长。负数/零切片参数还可能使循环和切片逻辑进入不可预测状态。

建议：

- 限制单消息大小、单会话累计音频时长/字节数、context 长度、并发连接数和待处理队列深度。
- 校验 `source in {'mic', 'file'}`、数值有限且落入允许区间、Base64 严格解码、字节数是 float32 帧的整数倍。
- 采用 `bytearray` 或 chunk deque，避免 `bytes +=` 的重复复制。
- 队列满时明确返回“服务器忙”，文件任务可退避，麦克风任务采用低延迟优先策略。
- 为连接建立 idle timeout、任务 deadline 和取消消息。

### AUD-04：调度算法与“公平”声明不一致（高）

修复状态：已完成。`TaskBuffer.pop()` 现在从 `OrderedDict` 头部取出一个 task 的最早片段；该 task 仍有积压时将其移至尾部，没有积压时删除缓冲，从而实现跨 task 的 round-robin，同时保持同 task FIFO。测试已覆盖 3 个 task 轮转、持续生产者、断线清理和单 task FIFO。

原始证据（修复前）：`TaskBuffer` 文档写“跨 session 轮转”，但 `pop()` 使用 `next(reversed(self._buffers.items()))`，每次都选择最后插入的 task_id，且没有 `move_to_end()` 轮转。

影响：最新任务只要持续有分片，旧 task 就可能长期得不到处理。多个文件转录和实时听写同时存在时，延迟与提交先后相关，难以预测。

建议：使用真正的 round-robin：从 OrderedDict 头部取一个 task，若该 task 仍有积压则将 key 移到尾部。进一步可以使用两级队列，为 `mic` 提供低延迟权重，但设置文件任务最低服务份额，避免两类任务互相饿死。测试至少覆盖 2/3 个 task、持续生产者、断线清理和单 task FIFO。

### AUD-05：缺少工程质量门禁（高）

### AUD-06：音频缓存没有按 task 隔离（中）

修复状态：已随 AUD-03 完成。`ws_recv()` 现在维护有数量上限的 `dict[task_id, AudioCache]`，会话内固定 source、切片参数、context 和 language，并在 final、超时或断线时清理。

原始证据（修复前）：`ws_recv()` 为整个 WebSocket 创建单个 `AudioCache()`，之后所有消息都写入该缓存；缓存自身不保存 task_id/source/context。

影响：当前客户端通常串行工作，所以问题可能长期隐藏；一旦同连接并行文件转录、快速切换任务或消息重试交错，最终片段可能包含另一个 task 的音频，结果和归档也会错配。

建议：维护 `dict[task_id, AudioSession]`，会话内固定 source、切片参数和 time_start；首帧创建，后续帧必须一致，final/超时/断线时清理。限制每连接并发 task 数。

### AUD-07：环境不可复现（中）

证据：两个 requirements 文件只列包名，没有任何版本上下界；项目没有锁文件或受支持 Python 版本声明。代码已经针对 `websockets >= 14/16` 做参数分支，说明依赖行为确实在变化。审计环境实际可用的是 Python 3.12.10，而 `CLAUDE.md` 记录的特定 conda 路径并不存在。

影响：新装环境、打包机和用户机器可能解析到不同的 NumPy、websockets、onnxruntime、Pillow 或 PyInstaller，产生 API/ABI 兼容问题。

建议：声明支持的 Python 小版本；把直接依赖放入项目元数据并设置合理上下界；为 Windows CPU/DML/Vulkan 建约束或锁文件；发布构建使用锁定哈希；定期由自动化 PR 升级，而不是每次安装隐式升级。

### AUD-08：LLM 密钥管理容易误用（中）

证据：`LLM/*.py` 暴露并直接消费 `api_key` 字段；被 Git 跟踪的 `LLM/大助理.py` 含一个类似 Key 的掩码字符串。

影响：用户很容易把真实密钥写入同一位置后提交。掩码值不是有效凭据，却可能让用户误以为角色已经正确配置。

建议：仓库只保留 `api_key_env = 'DEEPSEEK_API_KEY'` 或本地 secrets 文件引用；启动时检查掩码/占位符并给出清楚错误；加 secret scanning（如 gitleaks）；若该字符串曾经由真实密钥产生，应在 Provider 后台确认轮换。

### AUD-09：隐私承诺与数据生命周期缺少统一说明（中）

证据：客户端默认 `save_audio=True`，会写日记；客户端和服务端日志记录完整或截断的识别结果/模型输出；启用云 LLM 的角色可读取选中文字、历史和热词并发给 Provider。README 强调“完全离线”，但联网角色是内置能力。

影响：本地优先不等于不留存；用户可能不知道语音、选区和识别文本保留多久，或什么时候离开本机。

建议：增加“隐私中心”：本地严格离线开关、云角色外发预览、音频/日志/日记独立保留期、一键清理、日志脱敏级别、首次启用云 Provider 的明确确认。README 将“完全离线”表述为“默认识别链路可完全离线，云 LLM 角色除外”。

### AUD-10：音频自愈仍是高竞态区域（中）

修复状态：部分缓解。`RLock` 现在串行化 `start()`、`stop()`、`reopen()` 和设备监控的关键区，消除了 AUD-01 的确定性故障，也避免多数生命周期操作同时进入 PortAudio。mock 测试验证了启动/停止幂等、驱动刷新顺序和 callback 线程边界。

剩余证据：finished callback 每次仍新建守护重开线程；设备监控每 4 秒检查并可能触发重开；闲置线程也会关闭/恢复流；退出仅切换运行标志，不 join 监控/重开线程。驱动刷新仍调用 sounddevice 私有 `_terminate()`/`_initialize()`。

影响：锁能把多个重开操作串行执行，却不会合并重复请求。设备拔插、蓝牙切换、闲置暂停、快捷键恢复和进程退出重叠时，仍可能连续 close/start、由旧回调重开新流或触发原生层 access violation。

建议：使用单独的 AudioLifecycleController 线程接收 `START/STOP/REOPEN/PAUSE/SHUTDOWN` 命令，所有 PortAudio 生命周期操作只在该线程执行。finished callback 只投递命令。对事件去重，并使用 generation ID 防止旧流回调影响新流。

### AUD-11：异常策略不一致（中）

证据：业务代码中存在大量 `except Exception` 和裸 `except`；`ws_send()` 捕获任意异常后立即继续无限循环。部分错误只写 debug，用户只能感知“没反应”。

影响：可恢复错误与永久错误无法区分，根因容易被吞掉；队列关闭或状态破坏后可能高速重试。日志本身也可能反过来拖慢程序。

建议：定义协议、设备、模型、认证、配置、取消等领域异常；只在系统边界捕获宽泛异常；永久错误让组件停止并通知托盘，瞬态错误指数退避；日志增加 task/socket/component 字段并限频。

### AUD-12：文档与配置漂移（低）

证据：README 快速开始描述 CapsLock/鼠标侧键长按，当前 fork 配置为右 Ctrl 和 X2、非 hold 模式；`CLAUDE.md` 标为 2.5-alpha，而配置版本为 2.6；其中列出的部分 LLM 角色文件已不存在，且机器专用 Python 路径失效。

建议：README 描述上游默认值时注明 fork 可能覆盖；启动时打印“实际生效快捷键”；版本只保留单一来源并由脚本同步文档；把机器私有环境偏好移出仓库级指南。

### AUD-13：仓库卫生与代码来源（低）

证据：`core/client/shortcut/shortcut_manager.py.bak` 被跟踪；三套引擎下存在大量相似 GGUF/转换代码；`.gitignore` 对 `*.spec`、测试和多种本地文件的规则过宽。

建议：确认 `.bak` 无独有内容后从版本控制移除；为 vendored 代码增加 `NOTICE`、来源版本和更新流程；能共享的只读 GGUF 工具抽成单份，模型特定差异留适配器；收紧 ignore 规则，避免重要测试/打包配置被悄悄忽略。

## 7. 功能改进建议

以下建议按“用户价值 × 当前架构适配度 × 风险”排序。

### 7.1 P0：可靠性与可配置性

#### 1. 首次运行诊断向导

自动检查麦克风权限、默认输入设备、采样、VC++ Runtime、FFmpeg、模型文件完整性、端口、防火墙、Provider 和 GPU 后端。提供 5 秒录音回放与本地识别测试，并生成可复制的脱敏诊断报告。

价值：显著减少“按了没反应”“没录到声音”“模型路径不对”的支持成本。

#### 2. 图形化配置中心

将 Python 配置迁移为带 schema 的 TOML/JSON，同时保留高级用户兼容层。界面支持快捷键录制、按键模式解释、设备选择、模型选择、切片参数校验、热词阈值预览和一键恢复默认。

价值：降低配置门槛，也能在保存前阻止非法切片、端口和密钥设置。

#### 3. 音频设备状态机与设备选择

提供“跟随系统默认”“固定设备”“设备丢失时回退”的策略，托盘显示当前设备；切换前后做短淡入/缓冲，避免蓝牙耳机切换导致崩溃或首字丢失。

价值：直接解决本 fork 正在修改的核心痛点。

#### 4. 安全的本机/LAN 模式

本机模式只监听 loopback；LAN 模式用向导生成令牌、显示二维码、限制客户端、支持 TLS/反向代理，并展示活跃连接和断开按钮。

价值：让 C/S 架构真正可安全跨设备使用，而不是依赖防火墙运气。

### 7.2 P1：效率与质量

#### 5. 批量转录任务中心

支持目录/多文件队列、优先级、暂停恢复、失败重试、断点续传、输出模板和任务历史。实时听写默认具有低延迟优先级，但保证文件任务最低吞吐。

#### 6. 识别质量对比与基准面板

对同一小段音频切换模型，显示准确度人工评分、RTF、首 token 延迟、显存/内存占用。保留本机硬件档案，帮助用户选择模型和参数。

#### 7. 热词工作台

在 UI 中展示“原词 → 候选热词 → 相似度 → 是否被黑名单拦截”，允许一键接受/撤销，并从用户纠错中生成候选词。加入按应用、语言和项目分组的热词集。

#### 8. 应用配置档案

基于前台进程切换 paste/type、末尾标点、自动回车、快捷键、语言、热词集和 LLM 角色。例如聊天软件、代码编辑器、交易软件各有独立策略。

#### 9. 隐私中心与严格离线模式

展示当前启用的外部连接、音频/日记/日志保存位置与大小；支持保留期、自动清理、加密归档和“严格离线”总开关。云角色触发前可显示将要发送的上下文类别。

### 7.3 P2：差异化能力

#### 10. 可选 VAD/智能结束

保持当前“无 VAD、保留上下文”的默认优势，同时提供可选的静音自动结束、长停顿分段和会议模式。VAD 只用于交互/切片，不强制截掉送入模型的必要上下文。

#### 11. 说话人、章节与字幕编辑

文件转录增加说话人分离、章节检测、字幕最大行长/CPS 校验和内置校对界面；支持重新对齐单段而不重跑全部音频。

#### 12. LLM 路由与本地降级

每个角色可声明 `local_only`、首选/备用 Provider、成本/超时上限和上下文白名单。云端失败时可降级为本地模型或原始识别结果，不阻塞上屏。

#### 13. 引擎插件接口

把 EngineFactory 的注册表扩展为稳定插件协议：能力、配置 schema、模型检查、推理、cleanup、版本兼容。第三方引擎不需要修改核心工厂文件。

#### 14. 可观测性与诊断包

增加结构化事件：录音开始、首包、排队、推理、合并、上屏；提供本地延迟瀑布图。诊断包默认脱敏，不包含音频、完整文本、密钥和选区。

## 12. 结论

这个 fork 的方向是有价值的：设备监控、状态提示和闲置挂起都直接改善日常语音输入体验。2026-08-08 的修复已经把协议安全、资源边界、任务公平性和自动测试从审计建议落实为代码与工程配置，AUD-01～AUD-06 的原始高风险问题均已有对应修复。源码双终端启动器和 FFmpeg 启动失败降级也改善了开发与异常场景体验。

剩余风险更集中，也更适合按边界治理：音频模块仍横跨原生音频库、回调线程和后台线程；依赖与构建尚不可完全复现；LLM 密钥、日志、音频、日记和云端外发还没有统一隐私控制面。现有质量门禁提供了继续重构的基础，但不能替代设备拔插、蓝牙切换、管理员窗口、GPU 推理和打包发布的 Windows 实机验证。

如果只选择三件事立即做，建议顺序是：

1. 将音频重开收敛为 single-flight 状态机，补齐退出 join，并完成 Windows 设备切换压力测试。
2. 锁定 Python 与直接依赖，跑通托管 Windows CI、发布 smoke 和干净机器安装/升级验证。
3. 将 LLM 密钥改为环境变量或本地 secrets，并建立严格离线、留存期和日志脱敏控制。

完成这三项后，配置中心、批量转录和热词工作台会更容易安全地迭代，也更适合向非技术用户发布。
