## 运行环境

- CapsWriter-Offline 2.6，Python 3.11.15。
- ASR：`qwen_asr` / Qwen3-ASR-1.7B。
- Encoder：ONNX Runtime CPU；LLM Decoder：Vulkan GPU，启动日志显示 29/29 层卸载到 `Vulkan0`。
- 识别语言：`auto`。
- 输入设备：系统默认的 `Headset (WH-1000XM5)`，单声道。
- 客户端采集：48 kHz、float32、2400 帧/块；发送前降采样为 16 kHz float32。
- 闲置挂起：已启用，20 秒后释放麦克风。

## 现象与时间线

1. 服务端约在 20:04:25 重新加载 Qwen3-ASR，之后两小时内多数任务正常。
2. 22:12:28 和 22:12:42 的相邻两次识别仍然正常。
3. 22:13:02 客户端因闲置释放麦克风。
4. 22:13:27 重新打开 WH-1000XM5；约 0.74 秒后收到首个音频块。
5. 22:13:34 和 22:13:41 连续出现两次幻觉输出。
6. 22:23:41、22:28:41 WebSocket 因空闲超时发生清理和重连；服务端进程及 ASR 模型没有重启。
7. 22:31:43 起，同一套模型、GPU 后端和麦克风重新得到正常结果，随后本次问题报告的其余语音也识别正常。

这说明故障具有间歇性和自行恢复特征。异常与一次蓝牙麦克风闲置恢复相邻，但更早的同类恢复曾成功，因此目前只能视为相关现象，不能认定为根因。恢复前发生过 WebSocket 重连，但 ASR Worker 不应依赖连接级状态，也暂时不能认定重连修复了问题。

## 复现与定因计划

- [ ] 人工试听两段异常录音，先区分“输入音频已经异常”和“清晰音频被模型错误解码”。
- [ ] 故障再次出现时，立即用同一保存音频连续转录 3 次，再在仅重连客户端、重启服务端后分别转录，保留每次原始模型输出。
- [ ] 增加脱敏诊断字段：Worker/模型连续运行时长、任务序号、设备、首块等待、实际块数、块间最大间隔、callback flags、RMS/峰值、推理后端和任务 ID 前缀。
- [ ] 当前代码在每次 prefill 前调用 `clear_kv_cache()`；增加运行时诊断以确认调用成功且缓存状态符合预期，并对异常输出实验性地重建 context 后单次重试。
- [ ] 对同一音频做 Vulkan/CPU A/B；如果 CPU 长时间稳定而 Vulkan 复现，继续检查驱动、量化模型和 GPU 数值稳定性。
- [ ] 对比 `input_device` 固定为笔记本麦克风、固定为 WH-1000XM5，以及启用/禁用闲置挂起四种组合。
- [ ] 至少运行 3 小时的循环语音 fixture，记录首次错误任务序号，并确认错误是否会在空闲、重连或上下文重置后恢复。

## 临时缓解建议

故障再次出现时，不要只继续说新句子覆盖现场。先保留当前音频并用同一文件复测；然后依次尝试客户端重连、服务端重启。若问题频繁出现，可临时固定输入设备并禁用闲置挂起做对照；若清晰音频只在 GPU Decoder 下错误，可暂时设置 `Qwen3ASRGGUFArgs.llm_use_gpu = False` 使用 CPU 验证稳定性。
