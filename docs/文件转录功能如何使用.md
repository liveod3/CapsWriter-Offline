# 文件转录功能如何使用

文件转录功能可以将音视频文件直接转为字幕或文本，支持批量处理。

---

## 一、准备工作

需要安装 [ffmpeg](环境依赖安装说明.md) 并确保其在系统 PATH 中。客户端启动日志 `logs/client_latest.log` 中显示 `[INFO] ffmpeg found` 即表示就绪。

---

## 二、使用方式

项目以源码脚本作为正式命令行入口。在项目根目录执行：

```powershell
conda run --no-capture-output -n capswriter python -u start_client.py transcribe "D:\Videos\lecture.mp4"
```

支持一次传入多个媒体文件和文件夹：

```powershell
conda run --no-capture-output -n capswriter python -u start_client.py transcribe `
  "D:\Videos\a.mp3" "D:\Videos\b.mp4" "D:\Courses"
```

文件夹会按路径稳定排序，只纳入 `config_client.py` 中
`file_media_extensions` 配置的媒体文件。默认是否递归由
`file_scan_recursive` 决定，也可以仅覆盖本次任务：

```powershell
# 强制递归扫描
python start_client.py transcribe --recursive "D:\Videos"

# 只扫描文件夹第一层
python start_client.py transcribe --no-recursive "D:\Videos"
```

可以用 `--format`（短参数 `-f`）精确指定本次保存格式：

```powershell
python start_client.py transcribe --format srt "lecture.mp4"
python start_client.py transcribe --format srt,txt,json "lecture.mp4"
python start_client.py transcribe -f srt -f txt "lecture.mp4"
```

允许值为 `srt`、`txt`、`json`、`merge`。一旦提供 `--format`，本次任务
完全按命令行值保存；省略时使用 `config_client.py` 的默认开关。格式参数只
控制最终文件，不会跳过 ASR 或时间戳对齐。

`--no-capture-output` 关闭 `conda run` 的输出捕获，`python -u` 关闭 Python
标准输出缓冲；两者一起使用时，发送进度、转录进度和当前文件会实时显示。

服务端必须已经启动；普通听写客户端可以保持运行。

### 打包版兼容

也可以将一个或多个音视频文件、文件夹直接拖拽到 `start_client.exe`。Windows
只会传入裸路径，客户端会自动判断为媒体转写，并使用配置文件中的默认输出格式。

支持批处理：可以同时选中多个文件一起拖拽。

旧式裸路径脚本调用继续兼容：

```powershell
conda run --no-capture-output -n capswriter python -u start_client.py "D:\Videos"
```

支持格式：几乎所有常见音视频格式（mp3, wav, mp4, mkv, flv, avi, mov 等）。

## 三、输出结果

转录结果文件会保存在**原文件同目录**，与原文件同名，仅后缀不同：

| 文件 | 内容 | 默认 |
|------|------|------|
| `.srt` | SRT 格式字幕，时间轴精确到句 | 生成 |
| `.txt` | 按标点分行的纯文本，方便阅读 | 生成 |
| `.json` | 字级时间戳 | 生成 |
| `.merge.txt` | 未切分的整段文本（长文） | 不生成 |

例如对 `lecture.mp4` 转录，会在同目录生成 `lecture.srt`、`lecture.txt`、`lecture.json`。

如果任一启用的同名结果已经存在，程序不会覆盖它，而是为整套新结果分配
同一个编号，例如 `lecture (2).srt`、`lecture (2).txt`、`lecture (2).json`。
终端和日志都会显示实际采用的编号及完整输出路径。


## 四、进阶：手动修正字幕时间轴

如果识别结果有错字，或想调整分行，可以这样操作：

1. 打开生成的 `.txt` 文件，修改错字、调整分行
2. 显式指定修改后的 TXT 和原始时间戳 JSON：

```powershell
python start_client.py rebuild-srt --text "edited.txt" --json "timestamps.json"
```

3. 客户端利用指定 JSON 中的字级时间戳重新生成 SRT，不会重新运行 ASR

这样就实现了**在保留原时间轴的基础上修正字幕内容**。

TXT 和 JSON 可以不同名，但两个文件都必须显式出现。打包版兼容同时拖入恰好
一个 TXT 和一个 JSON，程序会按扩展名判断角色；只传入其中一个会报错。若同名
SRT 已存在，新文件会采用 `(2)`、`(3)` 等编号，不会覆盖旧字幕。

## 五、配置项

在根目录实际配置 `config_client.py` 中（字段参考：[客户端默认模板](../config_templates/config_client_template.py)）：

```python
file_seg_duration = 60    # 转录时分段长度（秒），越大服务端内存占用越高
file_seg_overlap = 4      # 转录时分段重叠（秒），避免切分点丢字
file_scan_recursive = True  # 传入文件夹时递归扫描子文件夹
file_media_extensions = (...)  # 文件夹扫描允许的媒体扩展名
file_save_srt = True      # 是否生成 srt 字幕
file_save_txt = True      # 是否生成 txt 分行文本
file_save_json = True     # 是否生成 json 时间戳
file_save_merge = False   # 是否生成 merge.txt（未切分长文）
```

一般不需要改动。

命令行优先级如下：

- `--format` 覆盖本次输出格式；省略时使用四个 `file_save_*` 配置。
- `--recursive`/`--no-recursive` 覆盖本次扫描方式；省略时使用
  `file_scan_recursive`。
- 命令行覆盖只在当前进程生效，不会写回配置文件。

CLI 与客户端默认配置的对应关系：

| CLI 参数 | 未提供时的默认来源 |
|---|---|
| 无子命令 | 固定进入 `mic` 实时听写模式 |
| `transcribe --format` | `file_save_srt/txt/json/merge` |
| `transcribe --recursive/--no-recursive` | `file_scan_recursive` |
| `transcribe INPUT...` | 无默认输入，必须提供媒体文件或文件夹 |
| `rebuild-srt --text/--json` | 无默认输入，TXT 和 JSON 都必须提供 |

配置文件只需要一个 `file_scan_recursive`，不需要再增加互相矛盾的
`recursive` 和 `no_recursive`。两个 CLI 开关只是对同一布尔默认值的正、反向单次覆盖。

当前 `qwen_asr` 字幕链路的 GPU 配置位于 `config_server.py`：Qwen3-ASR 和
ForcedAligner 的 ONNX 编码器使用 `DML`，GGUF 解码器使用 GPU。修改后需要重启
服务端才会生效。ForcedAligner 仅在文件任务首次需要时间戳时加载，因此启动文件
转录前看不到它的 GPU 占用是正常的。

## 六、工作流程

```
脚本 transcribe 命令（或兼容拖拽媒体）
    ↓
检查 ffmpeg 环境
    ↓
ffmpeg 提取音频（16kHz、单声道、f32le）
    ↓
按 60 秒一段发送给服务端
    ↓
服务端 ASR 识别 → 时间戳对齐 → 拼接
    ↓
客户端接收结果 → 保存 srt/txt/json
```

## 七、常见问题

**Q: 转录结果时间轴不准确？**

- Qwen3-ASR 引擎需要配合 ForceAligner 模型才能生成精确时间戳，确认已下载该模型
- Fun-ASR-Nano 和 SenseVoice 自带时间戳能力

**Q: 能转录多长时间的音频？**

理论上不限时长，服务端会逐段处理。不排除超大文件会触发没有考虑到的 Bug。

**Q: 已经运行一个服务端和一个听写客户端，还能再启动文件客户端吗？**

可以。不同连接和任务的音频、文本及时间戳相互隔离，文件客户端不需要另起服务端。
当前服务端只有一个推理 Worker，各任务会轮转共享模型和 GPU；文件转录期间实时听写
不会串音，但可能等待正在执行的文件分片完成，延迟会比空闲时高。
